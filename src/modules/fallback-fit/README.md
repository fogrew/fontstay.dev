# Fallback fitting

Pure math with no parser, DOM or UI dependency. `FitFont` accepts sorted Unicode
scalar code points and corresponding glyph advances in font units. Inputs are
structurally compatible with the metrics format specified in the parsing spike.

`fitFont(target, fallback, weights, policy)` compares weighted advances on the
**intersection** of both fonts' coverage. Each advance is normalized by its own
`unitsPerEm`. `coverage` is the shared positive weight divided by all requested
positive weight; `missingTarget` and `missingFallback` identify omissions. Zero
weights are ignored. Combining marks with zero advances are valid; an entirely
zero-width average or no shared glyphs fails with a typed `FitError`.
Width accumulation normalizes against the largest shared weight independently
of coverage. A coverage ratio below floating-point range rounds to zero without
preventing fitting of the shared subset.

`fitFromAverages(target, targetWidthEm, fallbackWidthEm, policy)` supports existing
aggregate datasets. Both widths must already use the same character distribution
and be expressed in em. It cannot infer glyph coverage from an aggregate.

Results are unrounded ratios: `1` means `100%`. `sizeAdjust` is target width in em
divided by fallback width in em. Each vertical override is the target metric
divided by **target** `unitsPerEm`, then by `sizeAdjust`. Descent uses its absolute
value. Negative line gaps become zero because CSS percentages cannot be negative;
`lineGapClamped` signals that the original line gap cannot be reproduced.

## Vertical metrics

The default `freetype` policy follows FreeType's SFNT selection: flagged typo
metrics first, otherwise hhea; if hhea ascent and descent are both zero, nonzero
typo metrics, then Windows metrics with zero line gap. Explicit `hhea`, `typo` and
`win` policies select that source or fail if missing. `metricsSource` reports the
selection. Zero ascent/descent are allowed; negative ascent is rejected as
unrepresentable by CSS. Descents can use either signed or magnitude convention.

This is an engine policy, not a promise that every browser/OS selects the same
metrics. Audience-specific selection belongs to the browser support integration.
Variable-font inputs represent whichever instance was extracted. Width fitting
uses raw advances, without shaping, kerning, ligatures or contextual substitutions;
rendered-text optimization is a separate plan task.

## System fonts

`systemFonts` lists nine common system fallbacks (Arial, Helvetica, Times New Roman, Georgia, Verdana, Tahoma, Trebuchet MS, Courier New, Segoe UI) with hhea metrics and the Latin-weighted average advance (`xWidthAvg`) from `@capsizecss/metrics` 4.3.0 (MIT), converted to em. They feed `fitFromAverages` when no glyph data for the fallback is available, so the fit is limited to Latin text and uses Capsize's English weighting.

## Reference tests

`lib/reference.json` stores unmodified metrics from `@capsizecss/metrics` 4.3.0
and outputs generated by `@capsizecss/core` 4.1.3 `createFontStack`, with `subset:
'latin'` and `fontFaceFormat: 'styleObject'`, for Inter → Arial and Roboto → Arial.
The test compares the aggregate API with these frozen percentages to within
0.00005 percentage points, accounting for Capsize's four-decimal rounding.
This tests aggregate formula parity; it does not claim that a different corpus,
font version or metric policy produces the same measured average.

## `unicode-range`

`lib/unicode-range.ts` compacts code points into sorted, disjoint ranges (lossless),
formats and parses CSS `unicode-range` values (`U+20-7E, U+A0`), counts and
intersects ranges, and reports coverage of named subsets (`SUBSETS`: latin,
latin-ext, vietnamese, cyrillic, cyrillic-ext, greek, greek-ext). The subset
definitions follow the `unicode-range` values served by the Google Fonts CSS API.

## Why Trebuchet MS often wins on Windows

Study for #412, input to #411. Fifteen Google Fonts families (Open Sans, Roboto, Inter, Lora, Merriweather, Montserrat, Poppins, Lato, Nunito, Playfair Display, Source Sans 3, Noto Sans, Work Sans, PT Serif, Raleway; default instance, English profile) were parsed with the app's parser and ranked by `rankFor` for Windows over its 18 candidates.

- **Frequency.** Trebuchet MS is first for 3 of 15 (Open Sans, Lora, Work Sans), second for Playfair Display and fifth to fourteenth for the rest. It wins for wide-ish faces whose fit needs about +3% (Open Sans 1.028, Lora 1.027), not for most fonts. Tahoma, Palatino Linotype, Segoe UI and Arial take the other first places.
- **Why it wins.** Predicted shift is a step function: 2 to 18 of the 18 candidates (median 11) score exactly 0 at every viewport, so the order within them is set by the small terms: `0.05 * |ln(sizeAdjust)|` plus `0.05 * widthMismatch`. Trebuchet MS is the Windows font whose natural width (1.022 of Arial) is nearest to those web fonts. For Open Sans: Trebuchet MS cost 0.0016 (size-adjust 1.0283), Palatino Linotype 0.0023, Tahoma 0.0025, Segoe UI 0.0030. The gap between first and second is at most 0.0009 for every font tested (median 0.0003), so the choice among the zero-shift group is nearly arbitrary.
- **Not a data artifact.** Trebuchet MS is measured from glyph advances (not latin-only, coverage 100%). Its Latin-weighted width relative to Arial is 1.0223 measured against 1.0230 from Capsize; Tahoma, Segoe UI, Verdana, Georgia and Times New Roman agree within 0.1% too. The hhea metrics (1923/-455/0 per 2048) match the Capsize table. No weight or data change is made.
- **Real effect of the weights.** Where predicted shift is non-zero it dominates (Open Sans: Arial and Georgia score 0.0183 from a line-wrap flip and fall to ninth and tenth). Closeness to 100% matters only as a tie-break.

Consequence for the UI (#411): the list order is by predicted layout shift first and then by closeness of size-adjust to 100% and width, so the number shown next to a font is not the sort key and values above 100% are normal.


## `unicode-range` and split shaping

Spike for #419. Chromium 156 (Windows), 40 paragraphs of about 270 characters, 4x CPU throttling, median of 180 forced relayouts per cell. The web font (Fira Sans) is limited to `U+20-7E` and the fallback is `local(Arial)` with and without `unicode-range: U+20-7E`.

| Text | Without range | With range | Fonts used (with range) |
|---|---|---|---|
| Latin | 5.6-6.2 ms | 5.6-5.7 ms | web font only |
| Latin + Cyrillic | 11.7-12.0 ms | 11.1-11.9 ms | web font, Arial |
| Digits, currency, quotes, symbols | 11.2-17.6 ms | 10.5-12.5 ms | web font, Arial, Times New Roman |
| One accented letter per word | 8.5-10.5 ms | 8.4-9.2 ms | web font, Arial |

Runs vary by about 10% and the order of the two variants is not stable, so the option has no measurable layout-time cost. The set of fonts that draw a page is decided by the web font's coverage, not by the option: characters the web font lacks need another font either way, so a word with one such character is split in both variants. The option only changes which font draws them: the adjusted fallback without it, the generic family with it (with `local("Times New Roman")` as the fallback, the uncovered Cyrillic went to the adjusted Times New Roman without the range and to Arial with it). The only extra font seen was when the generic family lacked a symbol that the system fallback supplied, one more run for 3 of 287 glyphs.

Generated ranges do not overlap between fallback families. Within one family the broad rule is declared first and the per-script rules (Latin, Cyrillic, Greek spans, which are disjoint) after it, so the browser's reverse-order check meets the specific rule first. The face with the real glyphs is the site's own web font, a separate family.

Decision: keep the option and its default unchanged. The checkbox note already says that characters outside the range use the generic family; the measurement does not justify a stronger warning. No follow-up issue.

## Split web font audit

`auditSplitFaces(rules)` (`lib/split-audit.ts`) is a pure function over `@font-face` rules (`family`, `weight`, `style`, optional `unicode-range` text). It groups rules by family, weight and style and reports, as informational `SplitIssue`s (rule positions, affected characters as a `unicode-range` value, their count):

- `latin-split`: basic Latin (U+20 to U+7E) is spread over more than one rule and no single rule covers all of it;
- `overlap`: two rules share at least 16 code points and a quarter of the smaller rule;
- `late-real-face`: the same, and the earlier rule has more code points than the later one, so the face with the real glyphs is declared before the rules that overlap it (browsers check overlapping rules in reverse order, so it should come last).

A rule without `unicode-range` covers everything. Wildcards (`U+4??`) are understood; rules with a malformed range are skipped. The thresholds keep the Google Fonts layout (`latin`, `latin-ext`, `vietnamese`, `cyrillic`, `cyrillic-ext`, `greek`, `greek-ext`, which share a few combining marks and a few Cyrillic letters) free of warnings in any declaration order. The input is untrusted: at most 1024 rules, 1024 spans per range, 128 rules per group for the pairwise check and 50 issues are processed. The generator shows the result for pasted CSS and for site imports, the CLI and the MCP server through `fontstay audit` and `audit_font_faces`. Background: [Split webfont text layout](https://www.ivankristianto.com/split-webfont-text-layout/).
